# AgentLoom 面试材料

## 项目介绍（约一分钟）

AgentLoom 是一个本地 Agent 应用开发与运行平台。我实现了可视化 DAG 编排、独立 worker 的持久化执行、LangGraph 人工中断恢复、SSE 追踪与真实来源关联。它解决的核心问题是：浏览器关闭、用户修改草稿、worker 崩溃或审批重复提交时，任务仍能按照确定的版本继续，执行记录也能被追溯。

模型是可替换的能力依赖，演示模式也必须经过完整后端。没有凭据时可以验证执行可靠性；真实模型协议用可注入 HTTP 替身测试，付费模型质量需要后续实测。平台没有宣称多租户、公网安全或外部 exactly-once。

## 难点一：画布可编辑，不代表图可执行

React Flow 提供画布交互，但不会替平台检查 DAG、节点参数、模板依赖或发布版本。我实现了前后端共同校验：唯一 Start/End、连线端点、无环、可达性、条件端口、必填项、工具白名单与祖先输出引用。

发布时复制 graph，数据库触发器禁止修改版本。运行绑定 version_id 和配置快照；草稿使用 revision 乐观锁。这样“在运行时编辑提示词”只会改变后续新版本，不能悄悄改变正在执行的任务。

首版选择串行 DAG 调度。编译器把业务节点与 router 编译为 LangGraph；Condition 激活真假路径，汇合采用 OR 激活。串行设计更容易解释恢复边界，代价是无法利用独立分支并行。框架循环与用户图有环是两个层次，前者是内部调度实现，后者在产品层禁止。

**验证：** 有效图、环、非法变量、条件真假路径与汇合测试；实际浏览器创建、改属性、撤销重做、自动保存、发布和运行。可继续增强：结构化输出 JSON Schema、分支支配分析、更清晰的可选变量合并节点。

## 难点二：检查点之外，还需要任务生命周期

LangGraph 检查点保存图进度，但不会自动成为本项目的持久化队列。我使用 PostgreSQL 任务表，事务内 SKIP LOCKED 领取、owner 与租约、独立心跳、过期扫描与恢复上限。

只用租约可能在心跳延迟时重复启动同一图，尤其框架检查点写入不在业务节点事务里。因此整次 invoke 持有 run 级 advisory lock，恢复必须先获取同键的事务锁；节点提交还会核对 owner。正常崩溃释放数据库连接，新的 worker 才接管。

节点结果和 node.completed 同事务落盘，检查点由框架随后写入。若在两者之间崩溃，新的执行器先命中已完成节点缓存，补走图进度而不重发完成事件。模型与尚未提交的只读工具仍可能被重放，不能据此宣称外部操作 exactly-once。

**验证：** 子进程在 Start 结果提交后 `os._exit(17)`，新 worker 过期恢复，检查完成事件仍只有一次；并发领取测试；活跃 advisory lock 阻止错误接管测试。

**取舍：** 单 worker 优先正确性。没有分布式压测，也没有声称在网络分区中解决所有外部请求的不确定性。持有锁的卡死进程需要人工终止。大规模任务可引入专门队列和 fencing token 协议，但仍要维护业务幂等。

## 难点三：审批是一项一致性协议

审批节点用 interrupt 挂起，PostgresSaver 保存检查点；worker 随后将 run 标记 paused 并释放线程、心跳、连接和锁。决策使用 Command 恢复同一 thread_id。

审批记录有 run/node 唯一约束。API 原子校验 pending + paused、写入决策与 queued、记录 approval.resolved。太早审批会被拒绝，重复审批返回 409。恢复时按检查点中的 approvalId 选择决策，避免多个审批节点之间误用旧决策。

**验证：** 真正停止 Python 进程，启动另一个进程后确认并恢复同一任务；编辑后的报告保持一致；重复审批冲突；拒绝审批失败；暂停任务可取消。

**取舍：** 首版没有复杂审批角色和多人会签。审批等待不计入活跃运行时间，源内容与审批决策会保存在本地数据库。

## 难点四：取消请求不能冒充执行结束

正在执行的任务先进入 cancelling。worker 在节点、工具和流式 chunk 边界检查状态，真正离开执行过程后才提交 cancelled。如果还在等待同步 HTTP 请求，UI 就继续显示取消请求中。

租约过期只能说明心跳失联，不能证明外部请求停止。因此失联取消会进入 needs_attention，而不是伪造已取消。 queued 和 paused 没有活跃执行，可以直接取消。

**验证：** 排队、执行中、暂停三种取消；失联取消保守地标记人工检查。后续可增强每次外部请求的细粒度取消与平台级作业超时隔离。

## 难点五：SSE 可靠性来自持久化重放

SSE 是传输方式，不是事件存储。我先在 PostgreSQL 分配每个 run 的递增 eventId 并提交事件，再由 SSE 按游标读取。关键完成事件与节点结果使用同一事务。

客户端用 eventId 去重、按 70ms 批次合并文本。断线重连携带游标，页面刷新重新读取快照和历史事件。错误前的文本仍可追踪。重试按 attempt 展示最新尝试，旧尝试留在时间线。

**验证：** 后端比较 Last-Event-ID 与历史补拉序列；前端重叠事件不重复追加；浏览器刷新后仍展示已完成输出。首版数据库轮询适合单用户，规模变大时可加入通知层降低轮询成本，但不能丢掉事件存储。

## 难点六：引用可追溯，不等于回答已正确

文件链路保存原始字节、PDF 页码、分块序号、ID、模型空间签名。模型与 Embedding 分开配置，切换向量空间必须重新索引。检索结果是实际 pgvector 余弦距离查询，并保存在运行快照里。

最终 `[chunkId]` 必须来自本次命中的分块。伪造标记会被移除，并产生审计事件。来源面板提供这次命中的原文及源文件。但来源存在只证明可追溯，不能证明每句话被资料支持；仍需要人工检查与回答评测。

**验证：** 上传和源字节一致、分块关联正确、无效文件类型被拒绝、扫描 PDF 提示 OCR 不支持、虚构引用被拒绝；8 题 / 3 块 Recall@k 烟雾评测。演示替身是字符特征，不可包装成真实语义模型的效果数据。

## 性能：讲方法和环境，不编提升比例

优化点是 memo 自定义节点、稳定 nodeTypes 与回调、未改节点对象引用不变、节点只订阅自己的执行状态、拖动帧只改位置、拖拽开始记一次历史、结束发一次保存信号。节点删除与相关连线构成同一个撤销动作。

实测使用同一画布与状态管理，100/300/500 节点及 99/299/499 边，各三次真实指针拖动。记录 RAF p50/p95、最大帧间隔、long task、历史与保存信号数。环境、原始样本与局限见 performance.md。**没有优化前基线，所以没有“提升 X%”结论。**

## 常见追问

**为什么不用 FastAPI BackgroundTasks？** 它不提供本项目需要的持久化领取、租约、重启恢复和跨请求生命周期，长任务应由独立 worker 拥有。

**为什么任务创建用幂等键？** 网络超时后客户端不知道创建是否成功，需要同一个键找回原 runId。请求哈希防止把同键用于不同输入。新的“运行”动作要生成新键，而不是永久复用。

**为什么不让模型运行任意 Python？** 首版目标是验证受限工具调用与恢复边界。代码执行引入隔离、权限、资源和副作用问题，超出首版边界。计算器只接受受限 AST，不调用 eval。

**为什么不是 exactly-once？** 数据库事务无法原子提交外部支付、发信或远端模型请求。检查点解决图进度，外部副作用仍需要外部幂等键、幂等接收端、outbox 或对账。

**什么已经验证，什么没有？** 已验证本地真实数据库、演示全链路、跨进程恢复、浏览器操作和 SDK HTTP 协议。没有真实付费凭据，所以供应商连通性、实际回答质量没有验证；Docker 全镜像构建受当前网络超时影响；多 worker 大规模压测未做。

**下一步优先什么？** 外部真实模型场景验证、更多恢复故障注入、结构化报告与引用蕴含评测、活跃时间更精确记账、事件保留策略，再考虑鉴权、图并行与更大规模部署。
